На этой странице зафиксированы результаты исследования популярных статических фреймворков документации, проведённого 2026-10-12, и окончательное решение по фреймворку сайта документации этого репозитория.

## Журнал решений

| Дата | Решение | Обоснование |
| --- | --- | --- |
| 2026-10-12 (день исследования) | **Принять Astro Starlight, мигрировать с VitePress** | Starlight по умолчанию не отдаёт клиентский JS, фреймворк-нейтрален и лучше всего соответствует философии этого репозитория «ноль JS во время выполнения»; три дата-управляемые справочные страницы были переписаны как чистые Astro-компоненты, что позволило полностью убрать три зависимости — vue / vitepress / vite; порог Node >= 22.12 приемлем |
| 2026-10-12 (день исследования, предварительная оценка) | Оставить VitePress | На тот момент выгоды от миграции не покрывали затрат — семь сайтов семейства работали на VitePress, а сайт документации этого репозитория был полностью готов. **Этот вывод был заменён решением о миграции, принятым в тот же день, и сохранён ниже как историческая запись** |

Миграция была выполнена за один раз (Astro-каркас был построен, а все страницы перенесены в рамках одного коммита, чтобы избежать промежуточных небособираемых состояний). Остальные сайты семейства продолжают использовать VitePress; **этот репозиторий не требует от семейства унификации**; если в будущем семейство решит unifyировать фреймворк, практика Starlight этого репозитория послужит готовым ориентиром.

## Итоги исследования (историческая запись на основе данных 2026-10-12)

- **Если бы проект начинался с нуля сегодня и без ограничений семейства**, лучшей альтернативой был бы **Astro Starlight** — производительность, фреймворк-нейтральность, ноль клиентского JS по умолчанию, максимальное совпадение с философией репозитория «ноль JS во время выполнения». (Именно это суждение в итоге и привело к решению о миграции выше.)
- **VuePress фактически остановился в развитии, не рекомендуется для любых новых проектов** (последний пуш в репозитории — 2024-08-07, v2 до сих пор в rc).
- Единственное, за чем имело смысл следить до миграции — **VitePress 2.0** (на тот момент тег `next` указывал на 2.0.0-alpha.20, стадия alpha).

## Плюсы и минусы по эшелонам

### Первый эшелон: VitePress / Docusaurus / Astro Starlight

**VitePress** (использовался до миграции; остальные сайты семейства продолжают его использовать)

- Плюсы: однофайловые компоненты Vue можно писать прямо в markdown (именно на этом строились три справочные страницы этого репозитория — токены / контракты компонентов / золотые сценарии); **data loaders на этапе сборки** (`*.data.ts`) идеально подходят для чтения JSON-источника, а в dev-режиме с `watch` по glob дают горячее обновление; Vite dev чрезвычайно быстр; тема по умолчанию работает из коробки и требует почти нулевой конфигурации; богатое китайскоязычное сообщество и материалы.
- Минусы: слабая поддержка MDX (вне экосистемы MDX); версионирование документации, i18n и другие Enterprise-возможности нужно строить самостоятельно или искать плагины; глубина кастомизации темы уступает Docusaurus; поиск на локальном индексе, на крупных сайтах работает mediocre.

**Docusaurus** (продукт Meta, крупнейшая экосистема)

- Плюсы: **плагин версионирования документации** (сосуществование нескольких версий) и **i18n** — самые зрелые среди всех фреймворков; экосистема MDX, система плагинов и инъекции в тему (swizzle) прекрасно проработаны; за спиной Meta, долгосрочная поддержка гарантирована.
- Минусы: тяжёлые зависимости на React-стеке, большой размер JS в сборке; много опций и высокая когнитивная нагрузка; его конвейер данных (жизненный цикл `loadContent`) для подключения к JSON-источнику более громоздок, чем loader VitePress; в семействе нет прецедентов.

**Astro Starlight** (фреймворк-нейтральный, эталон производительности; **используется в этом репозитории**)

- Плюсы: **по умолчанию ноль клиентского JS** — максимальное совпадение с философией репозитория «ноль JS во время выполнения»; Content Collections дают типобезопасный слой данных; можно смешивать компоненты на Vue / React / Svelte; самый лёгкий результат сборки; документный опыт темы Starlight превосходен (боковая панель, навигация по якорям, встроенный i18n).
- Минусы: Starlight всё ещё 0.x (0.42.6), API может содержать breaking changes; Content Collections рассчитаны на **файловый контент** (md / mdx), а для чтения внешних JSON вроде `tokens/*.json` нужно обходить коллекции и подключать их напрямую в `.astro`-страницах (в этом репозитории проблема решена вызовом модулей codegen непосредственно из frontmatter); в семействе нет прецедентов, вопросы развёртывания / nginx / соглашения о боковой панели пришлось прокладывать самостоятельно (**в этом репозитории всё уже пройдено, см. [Описание развёртывания](../deployment)**).

### Второй эшелон: Nextra / Rspress / Fumadocs / Dumi

- **Nextra**: экосистема Next.js, сильный MDX, красивая документация; но жёстко привязан к Next.js + React, модель развёртывания (SSG / SSR / Edge) отличается от статического хостинга nginx семейства, а контракт содержимого v4 сильно отличается от VitePress. Мотивации для миграции нет.
- **Rspress** (продукт web-infra-dev из ByteDance): **самая быстрая сборка** (Rspack), на крупных сайтах с тысячами страниц заметно превосходит VitePress; дружелюбное сообщество мейнтейнеров, говорящих по-китайски. Но экосистема / плагинов меньше всего (20 тысяч загрузок в неделю), а стандартных парадигм data loaders нет — в этом репозитории всего 30 с небольшим страниц, и затраты на обучение ради скорости не оправданы.
- **Fumadocs**: самый быстрорастущий новичок последних двух лет (13,3k звёзд, всего 2 открытых issue), Next.js + современная дизайн-система, хороший поиск и переключение видов. Так же жёстко привязан к Next.js, а русскоязычных/китайских материалов мало. Стоит добавить в закладки, но вводить сейчас не стоит.
- **Dumi**: создан для **демонстрации библиотек компонентов** (live demo, автогенерация таблиц свойств). Этот репозиторий — хранилище токенов для этапа сборки, в нём **нет интерактивного UI для демонстрации**, так что ключевое преимущество совершенно не задействуется, плюс жёсткая привязка к Umi / React. Однозначно исключён.

### Третий эшелон и особые пункты

- **MkDocs Material / Sphinx** (Python-стек): крайне качественная документация, но требуют Python-инструментарий, что **не совпадает по экосистеме** со стеком Node >= 20 + pnpm + TS этого репозитория — невозможно повторно использовать TS-типы и функции загрузки codegen. Исключены.
- **docsify** (рендеринг во время выполнения): нет этапа сборки, подключается с CDN, подходит для маленьких документаций в стиле «одностраничный быстрый старт». Но он **не генерирует HTML на этапе сборки** (слабый SEO, медленный первый экран) и не позволяет запускать data loaders этапа сборки для проверки по схеме (на этой возможности и построены справочные страницы этого репозитория). Исключён.

## Посроковое сопоставление с ограничениями репозитория

| Ограничение / потребность репозитория | VitePress | Docusaurus | Starlight | Остальные |
| --- | --- | --- | --- | --- |
| Единая система с семью сайтами семейства (префиксы nginx / боковая панель / развёртывание) | ✅ используется на остальных сайтах семейства | ❌ пришлось бы прокладывать заново | ✅ в этом репозитории уже пройдено (три контракта nginx продолжают действовать, см. [Описание развёртывания](../deployment)) | ❌ |
| Чтение JSON-источника на этапе сборки для рендеринга справочных страниц | ✅ встроенный loader, реализовано | ⚠️ нужен кастомный плагин | ✅ реализовано (прямой вызов load / resolve codegen из frontmatter `.astro`-страниц) | ⚠️ больше хлопот |
| Один китайский язык, i18n не требуется | ✅ | преимущество не используется | ✅ | — |
| Текст + таблицы + код, без интерактивных демо | ✅ | ✅ | ✅ | ✅ |
| Дух «ноль JS во время выполнения» | ⚠️ runtime JS присутствует (только у сайта, не входит в зону красных линий) | ❌ тяжёлый JS | ✅ ноль JS по умолчанию | — |
| Повторное использование TS-модулей codegen (типы / валидация) | ✅ проверено (с vite ^5.4.21 SSR поддерживает `import.meta.dirname`) | ✅ | ✅ проверено (astro 7 включает vite 8, SSR поддерживает `import.meta.dirname`) | ✅ |

Дополнительные два соображения:

- Красная линия «ноль JS во время выполнения» регулирует **артефакты `dist/` codegen**, а не сайт документации. То, что сайт работает на фреймворке во время выполнения, не нарушает никаких красных линий — он полностью изолирован от `dist/`, а его сборка попадает в `.gitignore`. Впрочем, после миграции на Starlight сам сайт тоже стал по умолчанию отдавать ноль клиентского JS (только поиск / переключение темы и немного другого интерактива подгружаются по требованию), что ещё больше соответствует духу красных линий.
- Преимущества Docusaurus в версионировании документации и i18n в этом репозитории **не используются**: один язык, одна версия, содержимое следует за codegen — сценария «сосуществование документации по старым версиям токенов» не существует.

## Что продолжаем наблюдать

1. **Starlight 1.0**: репозиторий сейчас зафиксирован на `^0.42.6`. На стадии 0.x ещё возможны breaking changes; после выхода 1.0 оценим путь обновления (руководство по миграции Starlight перечислит все изменения).
2. **VitePress 2.0**: оценим после перехода в beta. Остальные сайты семейства по-прежнему на VitePress; главные вопросы — производительность сборки и поддержка Vite 7.
3. **Сигналы к пересмотру решения**: Starlight долго не поддерживается или семейный уровень принимает решение унифицировать фреймворк документации (тогда практика Starlight этого репозитория станет готовым ориентиром).
